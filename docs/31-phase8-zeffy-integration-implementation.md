## 1. Verified Zeffy capabilities (official source)

**Source.** The OpenAPI 3.1 document embedded in https://api.zeffy.com/api/docs ("Zeffy API" 1.0, read 2026-11-18). The page is JavaScript-rendered, so the spec was extracted from the page source. The support article (`support.zeffy.com/get-started-with-the-zeffy-api-yourg`) and `zeffy.com/integration/api` were also read.

| Topic | Verified fact |
|---|---|
| Base URL / auth | `https://api.zeffy.com`, `Authorization: Bearer <organization API key>` (generated by the organization owner) |
| Endpoints | **Payments:** GET `/api/v1/payments`, GET `/api/v1/payments/{id}`, POST `/api/v1/payments` (**records an OFFLINE payment**: cash, cheque, in-kind; "payment source is PublicApi"), DELETE `/api/v1/payments/{id}`. **Contacts:** GET/POST/PUT/PATCH/DELETE. **Campaigns:** GET (read-only). **Users:** GET. |
| Checkout creation | **None.** No endpoint creates an online, booking-specific hosted checkout session. |
| List payments | Filters: `currency` (cad, usd), `status` (succeeded, failed, pending), `type` (online, manual, imported), `contact`, `campaign`, `created[gte/gt/lte/lt]` (Unix seconds). Cursor pagination: `limit` (default 10, max 100), `starting_after` = `next_cursor`, `has_more`. |
| Money | `amount`, `eligible_amount`, `refunds[].amount`, `items[].amount`: "Amount in cents" (numbers). `currency` is lowercase (`usd`). |
| Payment status | Free string (example `succeeded`); the list filter documents succeeded / failed / pending. |
| Refunds and disputes | `refund_status` = none / partial / full. `refunds[]` entries have `{id, amount (cents), currency, status: pending/succeeded/failed, created}`. `dispute` is `{amount, status: needs_response/won/lost, reason}` or null. |
| Recurring | `recurring: {is_recurring, status, interval, subscription_id, current_period_start/end}` or null. Items carry `recurrence_interval`. No schedule or charge-plan endpoint exists. |
| Correlation fields | **`metadata`: "Reserved for future key-value pairs"** — no custom reference can be passed. Only `buyer_questions[]` and per-ticket `items[].questions[]` (custom questions answered on the form) are returned. |
| Ticketing | `campaign_category` (event, …), `occurrence_id`, ticket items with `rate_id`/`rate_title` and per-attendee `contact_id`. Zeffy issues its own tickets for ticketing campaigns. |
| Webhooks | Events: `payment.completed`, `payment.created`, `payment.updated`, `payment.deleted`, `contact.*`. `completed`/`created` carry the full payment; `updated`/`deleted` carry an **id-only** reference (fetch the payment; a 404 means deleted). Body: `{id, type, version, dispatchedAt, data}`. |
| Webhook signature | `Zeffy-Signature: t=<unix seconds>,v1=<hex>`, where v1 = hex(HMAC-SHA256(secret, `"{t}.{rawBody}"`)) over the **raw** body; compare in constant time; recommended tolerance 5 minutes. The signing secret is in Settings → Integrations → Webhook. |
| Retries | Non-2xx or timeout is retried with exponential backoff over **12 attempts within 3 days**. Each retry is re-signed with a fresh timestamp; the event `id` stays the same (idempotency key). |
| Rate limits | Per organization: **100/minute and 20/second**. A 429 response carries `Retry-After` (60 or 1 s). `X-RateLimit-*` headers are sent on authenticated responses. |
| Errors | Envelope `{error: {type, code, message, param, status, doc_url}}`. Codes: invalid_parameters, invalid_request (400); invalid_api_key (401); resource_not_found (404); rate_limit_exceeded (429); internal_error (500). |

**Not documented / unverified:**

- Whether the payment `amount` includes the optional Zeffy tip. (`payment.updated` lists "tip" among the fields that change.)
- Whether a hosted form accepts a pre-filled answer or a URL parameter.
- Whether items are one per ticket.
- The exact `status` strings beyond the list filter values.
- Whether `payment.completed` is sent for manual or imported payments.
- Refund notifications in practice.

The implementation fails closed on all of these (§4).

**The read API "eligible_amount"** is the tax-receipt-eligible amount set by Zeffy/SDI. MEKI stores it for display only and **never calculates** a deductible or fair-market value.

## 2. Existing architecture → Zeffy mapping

| MEKI entity (existing) | Zeffy entity | Identifier | Authoritative status |
|---|---|---|---|
| `EventBooking` (`EB-…`, created before payment, server-priced) | Payment on SDI's ticket campaign | `payment.id` (UUID) ↔ `EventBooking.providerReference` | Zeffy payment `status` + refunds, read via webhook or API; MEKI confirmation only through `BookingPaymentsService` |
| `EventBookingPaymentAttempt` (`BA-…`) | — (Zeffy has no session) | `providerSessionRef = zeffy:<payment.id>`, `providerPaymentRef = payment.id` (both unique per provider) | created only at the moment a verified payment is applied |
| `EventBookingTransaction` (ticket ledger, EVENT_TICKET_PAYMENT) | Payment / refund | `providerTransactionRef` = payment id / refund id | written only by the established pipeline |
| `Donation` (`DN-…`) and `PaymentTransaction` (donation ledger) | Payment on SDI's donation forms | `payment.id` | **not applied in 8A**: donations on SDI's forms are made directly on Zeffy and usually have no MEKI record (§4) |
| `RecurringDonation` | `payment.recurring.subscription_id` | subscription id | recorded on the provider record only; no schedule is derived |
| `Refund` (donation refunds, approval workflow) | `refunds[]` | refund id | Zeffy refunds are performed by SDI; MEKI only reads them |
| `PaymentWebhookEvent` (existing, unique `provider` + `providerEventId`) | Webhook event | `event.id` | durable receipt + processing status |
| **`ProviderPayment` (new, additive)** | Payment (read model) | unique `provider` + `providerPaymentId` | provider fields + MEKI correlation state |

**Mismatches between MEKI and Zeffy:**

- The existing webhook pipeline correlates events by the attempt reference echoed by the provider (`BA-…`). Zeffy cannot echo it because `metadata` is reserved. Zeffy events therefore use their **own route and processor**, and only reuse the event store and the booking confirmation/refund handlers.
- Payments that arrive with no MEKI record to attach to (direct donations, unmatched payments) had no home; they are what the new read-model table is for.

**The REST client (`zeffy.client.ts`):**

- **Operations:** list (cursor pagination, `limit` 100, `created` filters, page cap), get payment (404 → null), campaign title, ping.
- **Timeouts and retries:** 10 s timeout. Retries apply to GET requests only: on 429 it honours `Retry-After` (capped at 60 s); on 5xx, network errors and timeouts it backs off exponentially with jitter.
- **Errors:** typed `ZeffyApiError(status, code, retryable)`. IDs are validated as UUIDs before any request.
- **Never logged:** the key and response bodies.
- **Deliberately absent:** POST/DELETE payments and every contact write.

### Webhook processing (`POST /api/v1/integrations/zeffy/webhook`)

1. Reject bodies that are empty or over 256 KB.
2. If no secret is configured, answer **503** (Zeffy keeps retrying for 3 days instead of the event being acknowledged and lost).
3. Verify the signature on the raw body. Missing, malformed, wrong, stale, future or tampered signatures → 400, and **nothing is stored**.
4. Parse and validate the envelope. For `completed`/`created`, validate the payment object.
5. **Durably store** the event in `PaymentWebhookEvent` under the unique `(zeffy, event.id)`. The stored payload is sanitised: no buyer personal data or free-text answers, only the references found in them.
6. **Duplicates:** the same event ID is acknowledged as a duplicate. An event still RECEIVED within the last 60 s is not raced (it is being processed); a stuck one (over 60 s) or one that failed transiently is processed again.
7. **Process by event type:**
   - `completed` / `created`: upsert the provider record from the payload.
   - `updated`: fetch `GET /payments/:id`, which is the authoritative current state. A 404 marks the payment deleted.
   - `deleted`: mark it deleted and flag it for review; accounting is never reversed.
   - Other types (`contact.*`, unknown): IGNORED, with no financial effect.
8. **Final status:** PROCESSED, IGNORED, or FAILED with `TRANSIENT:` (retryable, e.g. API key missing for an id-only event) or `REJECTED:`.
9. **Out-of-order deliveries** cannot regress a record: an older snapshot never overwrites a newer one (`lastSyncedAt`).

## 4. Correlation and application rules

**Booking correlation (Gala ticket campaign).** A Zeffy payment is applied to a booking only when **all** of these hold (`decideGala`):

1. The campaign equals `ZEFFY_GALA_TICKET_CAMPAIGN_ID`. Otherwise the payment is IGNORED.
2. **Exactly one** `EB-…` reference is found in the buyer's or attendees' answers. None → UNMATCHED; several → review.
3. Status is `succeeded`.
4. Currency is `usd`.
5. Type is `online`.
6. There is no refund and no dispute, and the payment is not deleted.
7. The items are ticket lines only.
8. The booking exists and belongs to the Gala event (`ZEFFY_GALA_EVENT_CODE`).
9. No other provider payment has claimed the booking.
10. The booking currency is USD.
11. The amount in cents equals the booking total, the ticket lines add up to the same total, and the number of ticket lines equals the number of guests.
12. The booking is still PENDING and its payment UNPAID, PENDING or FAILED.

If any rule fails, the payment is set to **NEEDS_REVIEW** with the failed rule as the reason. **Payments are never matched by e-mail, name or amount alone.**

**Application** happens only when `ZEFFY_GALA_AUTO_CONFIRM=true` (test environments only). In one transaction:

1. **Claim the booking.** The unique `(provider, matchedEntityType, matchedEntityId)` index stops a second payment for the same booking.
2. **Create a Zeffy-bound attempt.** Its unique `zeffy:<payment id>` session reference stops the same payment from being applied twice.
3. **Call the established `BookingPaymentsService.handle('payment.succeeded')`.** It re-checks amount, currency and state; writes the ledger; confirms; issues one ticket per guest; and queues the PDF and e-mail jobs (outbox).

Any failure rolls the whole transaction back and leaves the payment in review. A run that loses a race never downgrades a payment that is already CONFIRMED. The evidence row is the verified webhook event, or for reconciliation an `api-sync:<id>` record (the authenticated API read).

**Refunds, disputes and deletions on an applied payment:**

- **Full refund** (sum of succeeded refunds = amount): the established refund pipeline sets REFUNDED and refunds the tickets.
- **Partial refund:** review only.
- **Dispute:** review.
- **Deletion:** review; accounting is never reversed.
- A refund is never inferred from a changed amount.

**Donations on SDI's forms:**

- They are classified (donation lines → CHARITABLE_DONATION).
- They are UNMATCHED when no `DN-…` reference is present, which is normal for gifts made directly on SDI's form.
- A matching `DN-` reference is flagged "awaits SDI (Phase 8B)".
- No MEKI donation record is created or changed in 8A: importing donor data and receipt ownership need SDI's decision.

**Recurring donations:** the subscription ID and interval are stored on the provider record. No schedule is derived, and collected totals still come only from actual verified payments.

**The architectural blocker:** Zeffy offers **no immutable correlation field** (`metadata` is reserved), and the only returned channel, a custom-question answer, is typed by the buyer. Until SDI/Zeffy confirm a reliable mechanism (doc 32 item 10), automatic confirmation stays disabled and refused in production.

## 9. Security considerations

- **Secrets:** never in browser code, logs or status responses; the admin status schema accepts booleans only (unit-tested).
- **Webhook authentication:** raw-body HMAC in constant time with replay protection, verified **before** any state change. Events are stored only after authentication.
- **Personal data:** buyer name, e-mail, address and free-text answers are not stored. Only the extracted MEKI references are kept.
- **API calls:** GET-only towards Zeffy; no offline-payment or contact writes; no card data anywhere.
- **Least privilege:** `payments.read` to view, `payments.manage` to reconcile or re-check. Every action is audited.
- **Fail-closed configuration in production:** official host only, no auto-confirm, mock provider forbidden.

## 11. Operational note: the dev API outage (resolved)

**Cause (reproduced).** `pnpm turbo run … build` runs the API's `prisma generate` and `nest build`, and `deleteOutDir: true` empties `dist/`. A running `nest start --watch` sees the change, restarts while `dist/` is gone, crashes with `Cannot find module dist/main`, and waits. A timestamp-only touch doesn't wake it.

**Workarounds:**

- Stop the watcher before a full build, or restart it afterwards.
- Or run builds from a separate checkout.

The build configuration was left unchanged; turning off `deleteOutDir` would leave stale compiled files.
